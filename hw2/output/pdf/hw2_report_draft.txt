Part 1: Implementing Mutexes

CSE113 Homework 2 - Report draft | Brian Lee | October 14, 2026

Design

The filter lock stores each thread's current level and one victim for each level. A thread moves through levels 1 through N-1. At each level it names itself the victim, then waits while another thread is at least at that level and it is still the victim. Changing its level to zero releases the lock. Each thread has a distinct ID, so only that thread writes its own level entry.

The bakery lock stores a choosing flag and a ticket for each thread. A thread sets its choosing flag, scans all tickets, chooses one larger than the maximum, and clears the flag. It waits for every other thread to finish choosing, then waits for any smaller (ticket, thread ID) pair. IDs break ties when two threads choose the same ticket. A zero ticket means the thread is not competing for the lock.

All shared algorithm entries are atomic and are accessed only through load() and store(), using the default sequentially consistent ordering. There are no atomic read-modify-write operations in either implementation. The number of threads and array pointers are ordinary variables because initialization finishes before workers start. Both submitted headers call std::this_thread::yield() in their waiting loops.

Function | Purpose, inputs, outputs, and assumptions
mutex() | No input. Initializes count to zero and pointers to null; the object is not ready to lock until init().
init(N) | Allocates and initializes arrays for N > 0 threads. Returns void. Called with no threads using the mutex.
lock(id) | Returns void with exclusive access. Requires a unique ID in [0, N-1], initialization, no recursion, and no bakery ticket overflow.
unlock(id) | Returns void after releasing the caller's lock by clearing its level/ticket. Requires a matching lock(id).
~mutex() | Deletes the arrays after all users finish. These objects are not copied, and IDs are not shared between live threads.

Analysis

The C++ mutex has much higher throughput than the custom locks in the Docker runs. The custom algorithms scan shared arrays, and the filter lock repeats that work at N-1 levels. At 10 threads, however, the custom locks generally distribute acquisitions more evenly. Increasing the thread count makes spinning especially costly: the scheduler can pause a thread that other threads need to advance. Yielding gives waiting threads an opportunity to let runnable competitors proceed, which greatly improves the oversubscribed custom-lock results. The native table also shows that the effect depends on the host scheduler; yield is not a guarantee of better throughput in every configuration.

The very large filter/no-yield CV at 40 threads is consistent with uneven scheduling and staggered worker startup. The histogram sensitivity check changes the numerical CV but does not erase the underlying variability; dropping a busy thread can also hide real unfairness. Other likely sources of variation are background activity, the host's different CPU core types, and the short measurement period. The bakery/no-yield Docker runs at 40 threads record zero measured acquisitions: the total acquisitions remain within the 501-event warmup, so zero does not prove deadlock and cannot be described as perfect fairness. I retained all trials, including these zeros and the large histogram bins, to keep the comparison transparent.

Part 2: A Fair Reader-Writer Lock

Design

The fair lock follows the default lock's structure and adds a waiting_writers counter. One internal std::mutex protects the active-reader count, writer flag, and waiting-writer count. A reader may enter only when no writer is active or waiting. A writer registers itself before waiting, then enters after existing readers leave and no writer is active. Registering a writer closes the gate to new readers, allowing the current readers to drain. When there are no writers, readers follow the default path with only one additional counter check; no condition variables or extra reader-side locks are used. This is writer preference, not a FIFO guarantee: continuous writers can delay readers, and writer ordering depends on scheduling.

Function | Purpose, inputs, outputs, and assumptions
rw_mutex() | No input. Initializes reader and waiting-writer counts to zero and writer to false.
lock_reader() | No input; returns void once shared access is acquired. Multiple readers can enter. Caller must not already own this lock.
unlock_reader() | No input; returns void after decrementing the active-reader count. Requires a matching reader acquisition.
lock() | No input; returns void with exclusive writer access. Registers one waiting writer, then removes that registration when admitted.
unlock() | No input; returns void after clearing the active-writer flag. Requires a matching writer acquisition.

The much larger writer count and lower reader count in the mixed workload agree with the design: readers cannot repeatedly bypass waiting writers. Part 3: A Concurrent Linked List

Design

All three stacks keep the original representation: start points to the first node, and the last node is the stack top. Every nonempty operation begins at start and traverses next pointers to the tail; there is no cached tail pointer and no reversal of the list. A node stores its integer value and next pointer. push appends, pop removes the last node, and peek reads the last node. The allowed input values are 0, 1, and 2.

The coarse stack holds one std::mutex for each complete push, pop, or peek, including traversal. The reader-writer stack uses one std::shared_mutex: push and pop hold it exclusively because they change links or destroy nodes, while peek holds it in shared mode so several readers can traverse together. Scoped lock objects release the lock even when an empty or single-node branch returns early. Holding the lock throughout traversal prevents a writer from deleting a node that a reader still uses.

SwapTop keeps the reader-writer stack's push, pop, and peek unchanged. It first takes a shared lock and traverses to the last node. If the list is empty, it returns; if the existing value equals the requested value, it also returns because there is no write to perform. The three-value input domain makes this shortcut useful, and the benchmark heavily favors zero. Otherwise it releases the shared lock, acquires an exclusive lock, checks for an empty list again, traverses again, and replaces the current tail's value. It never keeps a node pointer across the unlocked interval, since a concurrent pop could delete that node. The no-change case takes effect at the shared-lock observation, and the changing case takes effect at the exclusive-lock assignment.

Function | Purpose, inputs, outputs, and assumptions
Llist_node(d) | Creates a node with integer d and next = null. Nodes are allocated/linked only while holding the stack's writer/exclusive lock.
CSE113_Stack() | No input. Creates an empty stack by setting start to null, before worker threads launch.
push(p) | Requires p in {0,1,2}; returns void after appending one node at the tail.
pop() | No input; removes and returns the tail value, or -1 when empty. Handles the single-node case by clearing start.
peek() | No input; returns the tail value without removing it, or -1 when empty.
swaptop(v) | Only in the third stack. Requires v in {0,1,2}; returns void after replacing the current top, or does nothing when empty.


Experiment workflow and correctness

Each stack ran exactly three times per environment, starting with 1,024 nodes. Coarse and RW use four peekers, one popper, and one pusher. SwapTop adds four swaptoppers, so it has ten workers rather than six. Counts include attempted empty operations, not just successful pops. The benchmark generates zero with probability 997/1000 and one otherwise; value two is covered by correctness tests.

The tests check empty behavior, all legal values, LIFO order, changing and unchanged SwapTop calls, preservation of 600 concurrently pushed nodes, and mixed concurrent operations. The supplied sequential checks and Clang ThreadSanitizer wrappers also pass in the course container.

Analysis

In Docker, the RW stack's mean total is 1.80 times the coarse stack's, and its mean peek count is 2.18 times as large. This agrees with the expected benefit of allowing four peekers to traverse at once. On the native host, the RW/coarse total ratio is 0.60, showing that the exact benefit depends on the implementation and scheduler. Each traversal is still O(list length), so changes in stack depth can substantially change the cost of later operations. Docker coarse trial 1 reports 419,315 operations, compared with 173,436 and 172,401 in trials 2 and 3. This is a large spread, so the three-run average should not be treated as a precise stable rate; all three values remain in the average.

The SwapTop shortcut can share the read lock with peekers when the requested value already matches the tail. The benchmark's strong preference for zero makes this case more common than a uniform choice among three values would, so its throughput is specific to this workload. Actual changes require exclusive access and a second traversal; that adds work and competition with push and pop. The reported per-operation ranges show substantial variation in some runs. SwapTop also adds four workers and a new counted operation, so comparing its total directly with the six-worker stacks would confound algorithm behavior with workload size. Atomic benchmark counters, random-value generation, sleeping, background scheduling, and changing stack depth all contribute to the observed rates.
